## 二、尚存的四项可复现实现缺陷

### 1. 缓存命中会再次丢失 Training Log

位置：实际 WSL 副本 `rdagent/components/runner/__init__.py:28`，`CachedRunner.assign_cached_result()`。

缓存对象即使保存了完整 `stdout`，命中时也只把 `result` 拷到新实验，不恢复 `stdout`。尚未执行的基线实验也只恢复指标，没有恢复训练信息。

离线例子：缓存候选的 `stdout` 为 `[42] ... valid's l2: 0.998`，调用真实 `assign_cached_result()` 后，新实验仍为 `""`。这是对 LightGBM 正则修复的旁路，说明正常执行路径通过，并不代表命中缓存也通过。

建议：把缓存视为恢复完整执行结果，至少恢复候选与基线的训练摘要、运行信息和真实工件来源，保留本轮的假设与任务身份。旧缓存原本就没有摘要时，要标注缺失或有依据地重建，不伪造“训练成功、无异常”。需分别测试命中与未命中路径。

原运行是否触发：36 个主候选回测的缓存命中标记均为 False，因此这不是那晚 36 轮日志为空的根因。

### 2. 回测缓存键未包含实际实现代码

位置：`rdagent/components/runner/__init__.py:11`、`rdagent/scenarios/qlib/developer/factor_runner.py:65`。

当前键包含任务描述，以及本地补充的时间、市场、基础特征、日历和 YAML 指纹；但没有候选 `factor.py` 的内容。

离线例子：保持因子名、描述和声明公式不变，将实现从 `close / close.shift(1) - 1` 改成 `close / close.shift(2) - 1`，调用真实 `get_cache_key()`，前后键完全相同。修复错误实现时，这可能使新代码拿到旧实现的回测指标。

建议：缓存键加入当前及依赖因子的实际实现代码哈希、基础 Python 特征代码、执行协议版本。训练数据指纹也不能永久只依赖日历；相同交易日历下价格文件变化仍应使缓存失效。后者是额外边界，未将其说成本次失败用例已经证明的数据问题。

原运行是否触发：本晚全部候选缓存未命中，尚无证据显示因此复用了错误指标。

### 3. 同名去重写回了错误字段，实际任务并未被过滤

位置：`rdagent/scenarios/qlib/proposal/factor_proposal.py:185`。

代码计算了 `unique_tasks`，最终赋值给 `exp.tasks`；但真实任务集合是 `exp.sub_tasks`，编码器和后续执行路径都读后者。

离线例子：因子库已有 `already_accepted`，模型又返回 `already_accepted` 与 `new_signal`。执行真实 `convert_response()` 后，`exp.tasks` 只剩新项，而 `exp.sub_tasks` 仍有两项；旧因子继续交给编码器。

建议：过滤后再构建 `QlibFactorExperiment`，或同步更新 `sub_tasks` 与同长的 `sub_workspace_list`。全为重复时给出明确可处理的空候选结果。仅替换字段名还不够，必须检查任务—工作区对齐。

原运行是否触发：79 个名称均不同，没有重复生成已采纳因子的同名任务；此前发现的 Loop_9/17 是数值等价但名称不同，属于另一个去重范围缺口，不能用这个字段错误解释。

### 4. 联合流程的 SOTA 上下文键名不一致

位置：`rdagent/scenarios/qlib/proposal/quant_proposal.py:157` 与 `rdagent/components/proposal/__init__.py:48`。

联合提案器产出 `SOTA_hypothesis_and_feedback`，共享生成器读取 `sota_hypothesis_and_feedback`。首字母大小写不同，导致已准备的 SOTA 专区没有传到相应位置。

离线例子：准备一个已采纳模型，其训练日志含唯一标记 `BEST_MODEL_TRAINING_LOG`；真实 `prepare_context()` 产生的大写键中有该日志，但共享生成器读取的小写键为空。因子子流程已补 SOTA，不代表联合流程的另一份提案器也被修复。

建议：统一键名并对 `fin_factor`、`fin_model`、`fin_quant` 各自做一次实际 prompt 渲染契约测试，不只检查准备函数的返回值。联合流程的旧历史反转与固定样本数量提示也需要一并核对。

原运行是否触发：没有。该晚对象类型是 `FactorRDLoop`，不是 `QuantRDLoop`。这是切换到联合运行前必须处理的问题。

## 三、仍有信息未进入对应 Agent，但不能一律叫作漏接线

### 基础特征和准确研究设定缺少显式上下文

完整复查 36 个假设请求，基础 Alpha20 的具体特征名出现次数为零，CSI500 的明确名称也未出现。代码虽然有 `experiment_setting` 属性，但 `QlibFactorScenario.get_scenario_all_desc()` 拼接的是背景、源数据、接口、输出格式和模拟器说明，没有把完整研究设定及当前 `plan['features']` 发送给假设生成器。

这说明 Agent 不掌握明确的基础特征清单和研究契约；不能仅因 UI 显示了配置，就假定模型也看到了。属性本身可用于 UI，因此不能单凭“属性未拼入 prompt”断言违反既定 API；真正需要修复的是运行目标和 Agent 上下文不一致的效果。

具体建议：程序生成同一份研究契约，发送给生成器和评估器，包含股票池、Alpha20 公式、已采纳因子、标签可交易时序、切分、LightGBM 参数、策略、成本与采纳规则，并用唯一字段标记检查实际出站请求。

### 当前因子反馈阶段本来就没设计接收训练日志

原运行 36/36 因子反馈请求没有 Training Log。`factor_feedback_generation.user` 接收本轮任务与四个指标，不接收 `exp.stdout`；训练日志主要用于后续假设生成的 last/SOTA 模板。

因此正则修复后，“下一轮规划器看到训练日志”可以成立，但不能自动推成“本轮反馈分析器也看到了”。如果期望反馈分析器区分训练不足与因子失效，必须显式扩展其输入；这是反馈接口的设计补充，不是现有字段恢复就自动完成。

### 历史摘要与当前反馈的指标口径不一致

历史、last、SOTA 模板展示无成本收益/回撤；本轮反馈展示含成本收益/回撤。它们有不同用途，不能不加说明地当作同一组表现。应同时标明净/毛口径，并保证主决策指标一致。

### UI 的 Alpha158 Plus 标签与真实基础特征不一致

`experiment/prompts.yaml:164` 仍固定写 Alpha158 Plus，而实际 checkpoint 中 `plan['features']` 只有 20 项。这是展示与事实不一致；不能由这个 UI 标签断言实际训练过 158 因子，也不能断言 Agent 看到了该标签。

## 四、与论文不同，但属于运行模式或有意的本地修改

### 1. 只有因子子流程，没有论文完整联合优化

checkpoint 类型为 `FactorRDLoop`；启动脚本运行 `rdagent fin_factor --loop-n 36`。该模式在固定的 LightGBM 与策略下研究新因子，没有每轮选择 factor/model 的联合控制器。

R&D-Agent-Quant 论文 §2 描述的是因子—模型联合优化和自适应方向调度，代码对应 `quant.py`、`QuantRDLoop` 及 `quant_proposal.py`。这次运行是其受支持的一个子场景，不是完整论文复现。来源：[论文方法部分](https://arxiv.org/html/2505.15155#S2)。

特别是 last 模板要求发现训练问题后下一轮纠正，但 `fin_factor` 的生成器能改因子，不能直接改固定 YAML 中的 LightGBM 学习率、叶子数等。因此 Training Log 修复并不等于建立了模型修复权限与动作路径。

建议先决定实验目标：固定模型评估因子时，训练问题应标为需要配置诊断，避免强迫 Agent 用变形因子修模型；要复现联合优化，再单独校验联合调度、缓存和上下文后选择对应入口，不直接拿当前脚本的结果与完整联合系统比较。

### 2. SOTA 采纳规则已经从收益导向改成 IC 硬规则

`git diff HEAD` 显示，上游提示词主要按年化收益改善推荐，本地增加 `ic_accept_decision()`：IC 至少增加 0.0005 且 Rank IC 不下降，覆盖语言模型建议。

这是本地研究政策变化。Loop_34 的净年化超额收益虽较高，但 IC/Rank IC 降低，因此按当前规则拒绝是程序按配置执行，不是 LLM 没有遵循上游收益标准。

建议在运行 manifest、UI 和实际 prompt 中明确标为 IC-first，并以同一目标评价轨迹。若要对照论文或上游收益导向，应建立独立、预注册实验，不在看到结果后改变门槛。

### 3. 搜索范围被限定为确定性公式

本地 factor 提案器取消了上游 15 轮后鼓励机器学习因子的提示，改为全程使用确定性公式，理由是因子内部训练模型曾超时且可能重复下游学习。

这是有理由的工程约束，但搜索空间与上游提示不再相同。反过来，联合提案器还保留 6 轮后鼓励机器学习因子的旧提示。因此两个入口的研究行为并不一致。不能默认切换 `fin_quant` 后会保留 `fin_factor` 的所有保护。

### 4. 有编码知识，不等于有持久化研究经验记忆

最后 checkpoint 显示：`with_knowledge=True`、`knowledge_self_gen=True`，编码知识库有 79 个任务映射、21 项成功任务知识等；所以不能说本次完全没启用 RAG 或没有学习。

但 `knowledge_base_path`、`new_knowledge_base_path` 均为 None，独立新运行没有配置文件式知识库读写；原 checkpoint 仍能保存进程内状态，续跑不等于 fresh run。假设生成器自身只保存 `scen`、`targets`，研究轨迹主要靠历史模板输入，不是 FactorMiner 那种按金融评估失败原因检索的结构化经验库。

这属于能力与配置边界，不是关闭了所有记忆。要实现跨独立运行积累，需要明确配置知识库持久化，并把编码经验与金融研究经验分开设计。

## 五、对前次轨迹结论的修正

此前统计结论仍成立：只有 Loop_8 晋级，之后 27 轮未刷新最优，数值等价因子确实重复出现。但对成因应更谨慎：训练信息被过滤、SOTA 专区缺失、Trial 引用错位都会削弱输入条件，不能把全部表现归咎于 Agent 推理能力或搜索策略。

应先修复并验收数据流，再在固定预算、数据、模型与采纳规则下做新的对照运行。旧指标不会因修复自动变好，修复后的轨迹也还没有被本次工作实测。
